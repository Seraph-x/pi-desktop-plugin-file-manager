# File Manager

**English** | [中文](README_ZH.md)
Browse, read, and edit the files of the current project inside PI-Desktop's **right-hand work panel**: a full directory tree with per-type icons, a split layout whose left list collapses as a whole, syntax-highlighted editing and saving, PDF preview, image and audio/video viewing, structured CSV/JSON viewing, switching between the local folders of a multi-folder project (remembered per project), plus create, rename/move, copy path from the context menu, **Open with…** (a submenu listing the programs actually installed on this machine, filtered by file type, opening the entry in the chosen program), search by file name, **git integration** (marks which files are modified and which are new directly in the list, and shows the exact per-line change against the last commit), and **file watching** (files changed outside the editor are re-read and the list refreshes); the host can also ask the view to open a specific file — including a path outside the project that the host itself picked (session scratch directory / attachments).

## Features

- **Full directory tree**: lazy-loaded, expandable level by level, directories first. Every row's icon follows the file type — folders, code, JSON, Markdown, styles, HTML/Vue/Svelte, YAML/TOML, Shell, SQL, images, archives, fonts, lock files, and more each get their own glyph and colour; special names such as `package.json`, `Dockerfile`, `LICENSE`, and `.gitignore` win over the extension check.
- **Selection and hover are clearly distinct**: hover is a faint neutral tint that only marks the pointer position; selection is an accent background plus an accent bar on the left edge plus foreground text at medium weight, it survives the pointer leaving, and hovering the selected row darkens it one step further so selection never looks lost.
- **Context menu**: grouped into open-with, create, file management, copy path, view changes / reveal in folder, and refresh, with sorting. HTML, HTM, and XHTML files can be opened in the host's built-in browser from **Open with…**. Empty space in the list offers only create and refresh; files and folders show the operations that fit their type. Arrow keys, Home, End, Enter, and Esc work; items with submenus open on hover, `→` enters, `←` goes back one level.
- **Copy relative path / copy absolute path**: right-click any file or folder. The relative path is based on the folder currently being browsed (forward slashes); the absolute path is a complete path you can paste anywhere (built from that folder when the base is not the main folder). Success and failure both raise a toast carrying the copied text, so nothing silently does nothing.
- **Open with… (submenu)**: hovering the item expands it with the programs **actually installed on this machine**: the system default application, plus VS Code, Zed, Chrome, Edge, and so on — whichever are present. Choosing one opens the current entry in that program. **Filtered by file type** — editors can open anything (files and folders), browsers appear only for web files they can genuinely render (`.html` / `.htm` / `.shtml` / `.xhtml` / `.mhtml` / `.svg` / `.pdf` / `.xml`): opening `App.tsx` in Chrome only shows a plain-text loading page, which is noise, so it is not listed at all. Probing runs once at startup and is **cached per day** (a second window or a second start on the same machine the same day reads that cache), and it **never walks directories**: it reads the registry's `App Paths` and `StartMenuInternet`, looks for candidate command names on `PATH`, and runs one `stat` against a few fixed install locations — every step is O(number of candidates). When nothing is found, only "system default application" remains; no entries that do nothing when clicked.
- **Split layout, collapsible left list**: file list on the left, content on the right. The divider is draggable and its width is remembered; the leftmost toolbar button collapses the whole left side (the editor then fills the panel, re-expanding restores the previous width, and the collapsed state is remembered). A host request to open a file collapses it automatically, and after that your manual expansion holds until the next host request.
- **Switching folders inside a multi-folder project**: when the host registers a project as several local folders (`workspace.get` / the first handshake's `roots`, `projectId`), the folder name in the panel's top-left corner becomes the switcher — clicking it lists the folders of that group, marks the primary one, and checks the one being viewed; it is keyboard accessible (`aria-haspopup` / `aria-expanded`, Escape and clicking outside both close it) and works while the tree is collapsed. **With a single folder, or with an older host that sends no group information, the header is exactly as before** — no entry that does nothing. Switching restarts the tree, expansion, selection, search, and open files together, and still passes through the "unsaved changes" confirmation first — cancelling changes nothing. Which folder is being viewed is **remembered per project** (by project id when the host supplies `projectId`, otherwise by primary folder path; a remembered path is trusted only if it matches the current `roots`, otherwise the main folder is used; up to 20 projects are kept, evicted by most recent write) and a new project starts at the main folder.
- **Syntax-highlighted editing**: CodeMirror 6 with line numbers, find and replace, multiple cursors, bracket matching, and code folding. The grammar is loaded from the file name and covers TypeScript/TSX, JavaScript/JSX, JSON, Markdown, CSS/SCSS/Sass/Less, HTML, Vue, XML, YAML, TOML, Properties, Python, Go, Rust, Java, C/C++, C#, Kotlin, Scala, Dart, Objective-C, PHP, Ruby, Lua, Shell, PowerShell, SQL, Dockerfile, and Diff. Everything ships inside the bundle, works offline, and makes no network requests. `Ctrl/Cmd+S` or the toolbar button saves; **nothing is written when there are no changes**, the caret and scroll position stay where they were after saving (no jump back to the top), and the view always shows what is on disk. `Ctrl/Cmd+S` also works when focus is outside the editor (just after clicking the toolbar, or while the preview, table, or tree view is showing).
- **Markdown preview / edit toggle**: opening `.md` / `.markdown` / `.mdx` adds an edit/preview toggle to the toolbar. The preview supports headings, fenced code blocks (with the same highlighting), blockquotes, horizontal rules, ordered/unordered/task lists (nested by indentation), tables (with alignment), and inline code / bold / italic / strikethrough / links / images. The toggle choice is remembered.
- **PDF preview (read-only)**: opening `.pdf` scrolls continuously; it supports single-page / two-page / two-page (cover alone) layouts, previous and next page, jump by page number, zoom (10%–400%), fit width, and 100% actual size; fit width follows the panel and split sizes and is computed from the real size of the widest known page group in the current layout. Scrolling across pages keeps the ratio, the cover and a trailing odd page are not blown up, and lazy loading widens the basis when a wider page appears. Clicking **Navigate** opens the sidebar: **thumbnails** locate pages and mark the current one, **outline** shows the PDF's built-in nested bookmarks and jumps to them, and **document info** shows file name, size, page count, title, author, and dates; when there are no built-in bookmarks it says so. PDFs with a text layer allow selecting and copying text and full-document search (Chinese and English hits highlighted and counted, previous/next match, case-sensitive, whole-word, and regular-expression switches in any combination; an invalid regex is reported and its hits cleared, then restored once corrected; Enter / Shift+Enter jump, Escape closes); clearing the query or closing removes the highlights. `Ctrl/Cmd+F` opens search while focus is in the reading area. Scanned documents show the original image; there is no OCR. PDF.js, its worker, the font mapping, and the image/colour decoding assets all ship inside the bundle and work offline. The main view caches neighbouring pages; thumbnails render by visible range and release page resources that are no longer used; in a narrow panel the navigation sidebar overlays and collapses after a jump, and Escape closes it too. Switching files releases the document and the worker; the per-file limit is **24 MiB**.

  Regular-expression search runs per page inside a dedicated worker and does not re-parse the PDF; a page that takes longer than 1 second or returns more than 100,000 hits is stopped, its hits are cleared, and a notice is shown so the expression can be simplified and the search resumed. Clearing, closing, changing the search mode, or switching documents cancels the old task. If the worker does not respond, document teardown waits at most 1 second and still releases that document's fonts, filters, and listeners.
- **Image viewing**: png / jpg / jpeg / gif / webp / avif / bmp / ico / svg. Fits the window by default with an actual-size toggle; the footer shows pixel dimensions and file size, the stage is checkered so transparent areas are obvious.
- **Audio and video playback**: mp4 / m4v / mov / webm / ogv / mkv use the player, mp3 / m4a / aac / wav / flac / ogg / opus / weba use the audio bar. **No autoplay**; when a codec or container is unsupported you get a clear notice instead of a black rectangle.
- **CSV / TSV tables (paged)**: opening `.csv` / `.tsv` shows a table, **1000 rows per page** by default; the footer toolbar pages through it (first / previous / next / last), shows "current range / total rows", and changes the page size (100–5000, remembered). The first row is a sticky header, the leftmost column is a sticky row number, hovering highlights the whole row, a fully numeric column right-aligns, and a value truncated with an ellipsis reveals itself on hover. **Clicking a header sorts**: ascending → descending → unsorted (back to file order); an all-numeric column compares numerically, otherwise natural text order, and empty values always sink to the bottom. Parsing supports quoted fields, `""` escapes, embedded newlines, CRLF, and ragged rows; there is a 60-column cap and a 200,000-row parse cap, and exceeding either is explained in the footer. The toolbar switches back to source editing.
- **JSON collapsible tree**: `.json` / `.jsonc` / `.json5` can switch to a tree view that expands two levels by default, lays out at most 100 keys per node directly, and truncates long strings (the full value is in the tooltip). Non-strict JSON such as `//` comments and trailing commas does not break the panel — it shows "parse failed + reason" while the source view stays editable.
- **SQLite databases (read-only)**: `.db` / `.sqlite` / `.sqlite3` / `.db3` open directly — an overview at the top (size, page size × page count, encoding, SQLite library version, WAL notice), a **Browse** tab to pick a table or view and read the data (paged, header sorting, leading `rowid`, `NULL` greyed out, BLOBs shown by size only), a **Schema** button for columns and types / indexes / triggers / the original `CREATE` statement, and a **SQL** tab with a **read-only query box** (`Ctrl/Cmd+Enter` runs it, optional row limit, elapsed time and truncation notice shown).

  This is the **only preview type in the plugin that opens large files**: database bytes never enter the view, the main process fetches one page at a time.
- **Binary files stated plainly**: files with no previewable form, such as zip / apk / exe, report "binary file (zip, apk, exe, and so on), preview not supported" — no magic detection and no pretending to unpack.
- **File operations**: create file, create folder, rename, move to a directory.
- **Open with the default application / reveal in folder**: from a file's context menu (`fs.openDefault` / `fs.reveal`). The host performs both, with the same permissions and scope as the built-in Files view. After the project has switched folders, when the base is not the main folder the plugin sends an absolute path instead — those two host channels accept only workspace-relative paths, and a relative path would be resolved against the main folder, so a same-named file in the other folder would open; the host has a correspondingly narrow allowance for absolute paths under a folder root registered for the project (ADR 0253).
- **Search by file name**: paged search across the whole project; clicking a result jumps to and expands to that file.
- **Host requests to open a file**: the host can ask the view to open a file, and both delivery paths are handled (the `?piViewOpen=` payload on the view entry URL and the `view:open` push); the same request delivered twice is processed once. The three path shapes each have their own basis: **a project-relative path** is based on the main folder (if you are viewing another folder it switches back to the main folder first); **an absolute path under another root of the same project** switches to the root that contains it and opens it relative to that root (ancestors expand and the row highlights exactly as when clicking a search result); **an absolute path outside the group** (session scratch directory / attachments) keeps the 0.4.0 external behaviour — not in the tree, no row highlighted, base unchanged. Opening still passes through the "unsaved changes" confirmation and never silently discards edits.
- **Git integration (status + change content)**: every row in the file list carries a git badge — **green `A` added** (including untracked new files), **amber `M` modified**, **red `D` deleted**, **blue `R` renamed**, **purple `U` conflicted** — and the row ends with the number of added and removed lines against the last commit (`+N` / `−N`); **directories show the aggregate for their whole subtree** (the most notable state within it plus the number of affected files), so you can see which directory is dirty without expanding it. Hovering gives the full wording (staged or not, tracked or not). A one-line summary at the top of the left list shows the current branch and the count of files in each state ("working tree clean" when it is).
  After opening a changed file, the toolbar shows a **Changes** button (the context menu also has **View changes**); it opens a **line-by-line unified diff**: added lines on green, removed lines on red, line numbers on both sides, hunk headers keeping the enclosing function name, and **staged (HEAD → index) and unstaged (index → disk) sections labelled separately**; an untracked new file is shown as "every line added", and a deleted file still shows what it removed. Saving immediately updates the badges and the diff (the main process's status snapshot is invalidated on the spot).
  Status and diffs come from **the real git in the workspace** (the read-only subcommands `status` / `diff` / `rev-parse`, writing no index, touching no network, and never touching `.git/**`): index formats, rename detection, and `.gitattributes` end-of-line and filter normalization therefore all follow the user's own git version and can never disagree with `git status`. **When git is missing, the current folder is not a repository, or git times out, every marker disappears** while listing, reading, writing, saving, and deleting are all unaffected.
- **File watching (automatic refresh)**: a file changed outside this view — by an external editor, `git checkout`, a build output, another window — is noticed within a bit over a second and **re-read**, and the tree and list refresh with it (size, mtime, git badge, creations and deletions all follow), with no need to press refresh. The main process opens one recursive `fs.watch` on **the folder currently being browsed** (`persistent: false`, so the panel does not linger in the background; events under `.git/` and `node_modules/` are dropped, and credential paths are still never reported), debounces changes for 250 ms into a bounded history, and the view pulls the increment every 1.2 seconds (the host offers no channel for pushing to views, so a hidden panel skips that round).
  Three boundaries, stated plainly: (1) the open file is re-read automatically **only when there are no unsaved changes**; **with unsaved changes only a notice bar appears and the buffer is never overwritten** (silently discarding what you just typed is the worst kind of "automatic"), and the bar's **Reload** still goes through the existing unsaved-changes confirmation; (2) the plugin's own saves are recorded first, so a same-name event within 1.5 seconds does not count as an external change — otherwise every `Ctrl+S` would remount its own document and lose the caret and scroll position with it; (3) a batch of changes refreshes at most 8 directories, leaving the rest to the next round or a manual refresh.
  A **auto-refresh** switch at the top turns this off at any time (when the runtime does not support recursive watching the whole button is disabled with the reason given), and **both manual refresh buttons remain exactly as they were** — watching saves that one click and never replaces it. Switching project or folder moves the watch along, and unloading the plugin closes it.
- **Edit / preview / changes are one exclusive tab set**: for a file with git changes the toolbar is a single tablist — **Changes** sits in the same group as **Edit / preview**, so you can enter from either side and come back, and the content area **holds exactly one view at a time** (in 0.8.0 Changes was an independent switch outside the tablist, so "preview + changes" could both be on and two full-height views would crush into each other; 0.8.1 moved the decision into the single-valued `contentKind()` in `lib/pane.ts`, so it cannot happen again). The changes tab is offered only for text files.
- **Ignore rules**: when the project has `.gitignore` / `.ignore`, matching entries are hidden (the toolbar's eye button shows them again); **with no rule file at all, the tree shows every entry**.
- **Follows the host appearance**: light/dark colours and interface language (Chinese / English) follow the PI-Desktop shell, and the editor and preview highlighting follow with them.

## Installation

On PI-Desktop's Plugins page:

1. **Load development plugin** → select this directory; or
2. Use a `.piplug` package through **Install plugin package**. After installing an update, close and reopen the whole File Manager tab, or restart PI-Desktop, so the view loads the new code; the PDF refresh button only re-reads the document.

With the plugin installed, open a project and click **File Manager** under the **Plugin views** group of the switcher in the **header of the right-hand work panel**.

> This plugin has no command-palette entry and registers no panel window — it contributes exactly one view docked in the right sidebar (`contributes.views`). The host offers no channel to open a view from a command, so no misleading command is declared here.

## Development

```bash
cd views-src
pnpm install
pnpm typecheck
pnpm build      # output goes to ../views, which is committed and loaded by the host
```

`views-src` holds the source (React + TypeScript + Tailwind + CodeMirror 6); `views` is the committed build output. The build is a **single-file IIFE** with every dynamic import inlined — the host loads views over `file://`, where Chromium blocks `type="module"` and `crossorigin`, so a `fileProtocolCompat` plugin in `vite.config.ts` rewrites `index.html`.

PDF uses the `pdfjs-dist` legacy build and the `PDFViewer` multi-page component, and `pdf-assets-plugin.ts` embeds the classic worker, CMaps, standard fonts, WASM, and ICC resources into the bundle. `lib/pdfViewer.ts` handles continuous scrolling, two-page layout, zoom, and page caching; `lib/pdfFit.ts` records the widest known page group per layout so fit width does not depend on the scrolled page and only collects sizes for pages PDF.js has already initialized, avoiding a full prefetch just to compute a width. `PdfSidebar.tsx` provides virtualized thumbnails, bookmarks, and metadata, reusing the main view's cleanup events so a page currently on screen is not released. Resource reads inside the worker map to data URLs, so no CDN, local server, or module loading over `file://` is needed; the `https://pi-file-manager.invalid/pdfjs/` string in the source is only an in-package resource identifier and that address is never contacted.

`pdf-find-plugin.ts` adds asynchronous waiting and stale-result protection to the find API of the pinned PDF.js version, with the regex worker inlined in the IIFE; `pdf-lifecycle-plugin.ts` adds bounded waits and front-end resource cleanup to the main API's startup, page cancellation, and teardown. Both check the version and a unique source anchor, and must be re-checked after a library upgrade.

Desktop PDF and file-watch regression checks live in `tests/electron/README.md`; they run isolated Electron instances against synthetic documents and check the real production `file://` interface and its resource release. Run them alongside any later change to the related behaviour.

`main.js` is hand-written, dependency-free CommonJS: plugin dependencies are not installed, so never `require` a third-party package from it.

### Packaging

After the build and the desktop checks, run `node scripts/prepare-package.mjs` in the repository root. It produces `dist/runtime`, copying only `manifest.json`, `main.js`, the production `views/` (with third-party licenses), the README, and the CHANGELOG; source, test fixtures, QA scripts, and dependencies never enter the runtime package.

Then run PI-Desktop's official `PluginCheck` and `PluginPack` against **`dist/runtime`**. Development loading may still point at the repository root; a real install package uses the prepared runtime directory so the whole test tree is not packaged.

### Verification

```bash
cd views-src
pnpm typecheck
pnpm verify        # project groups / path jail + highlighting + Markdown + viewers + git + watch + PDF
```

`pnpm verify` runs nine checks that need no DOM, covering the nine chains where a failure would be silent:

- **`verify-roots.mjs`**: asserts the pure rules in `lib/roots.ts` — group shape (an older host degrades to a single root, names filled from the last path segment, the `primary` marker and ordering), memory keys (`p:` / `r:`), the selected root (a remembered value is trusted only on a hit, and a directory such as `Beta-old` that merely shares a name prefix does not count), the bounded LRU of remembered folders, and "a rewrite moves to the end". Finally it cross-checks the same-named constant and memory-key prefixes in `main.js`: the view and the main process are two independent implementations, and drift means the interface and the jail each resolve against a different base.
- **`verify-jail.mjs`**: a stub host drives the **real `main.js`** on a two-folder project where the selected folder is not the primary root, asserting the containment base as the observable: after switching to the sibling folder the tree and root-relative reads follow it, the primary root's files cannot be read relative to the sibling root, `..` and credential files are still refused, an absolute path under another registered root is normalized within the group rather than treated as external, the base is still the remembered folder after eviction and single-key writes, and an older host without `roots` behaves as before.
- **`verify-highlight.mjs`**: runs 17 real files through the full `file name → language resolution → load → syntax tree → highlighted tokens` chain, asserts that each produces enough distinct highlight classes, and negatively asserts that `.txt` / `.bin` / `.zip` / `.png` / `LICENSE` are not claimed. CodeMirror highlighting is the classic case of "report nothing when parsing fails" — grepping the bundle for strings misses runtime problems (the first version of this plugin was hit by it: the fallback highlighter in `basicSetup` overrode its own styles).
- **`verify-markdown.mjs`**: asserts the element tree the preview really produces (headings, lists, tables, task lists, nested emphasis), the link protocol allowlist, and that **no `dangerouslySetInnerHTML` exists** and raw HTML is escaped. One regression case watches specifically for "sharing a `g`-flagged regex while parsing inline content recursively", which hangs the preview and eats memory.
- **`verify-viewers.mjs`**: asserts 12 CSV parsing cases (quoted fields, `""` escapes, embedded newlines, CRLF, ragged rows, truncation and the column cap), paging slices (out-of-range page numbers clamp, a short last page, an empty table still has one page), numeric-column detection, both the valid and invalid JSON paths, and the rule for "which views a file offers and which one it defaults to". Tables and trees are the path that turns file content into interface: a broken parser throws nothing and simply shows something wrong.
- **`verify-git.mjs`**: two layers. (1) Fixed fixtures pin the **parsing** of git's three output formats — `status --porcelain=v1 -z` (where a rename under `-z` is "new path + one bare original path" as two records), `diff --numstat -z` (where binaries are `-\t-` and a rename leaves the path empty then appends two bare paths), and unified diff (hunk headers, line numbers on both sides, several hunks, binary notices); a parsing mistake shows up as "modified" displayed as "added", a silent error. (2) A **real temporary repository** is created and a stub host drives the **real `main.js`**, asserting the badges from `fm.list` (modified / added / staged / directory aggregate / `null` for unchanged rows), the status returned by `fm.read`, the exact changed lines from `fm.git.diff` (replacement, an untracked file shown as all added, staged sections, a deleted file), that credentials and out-of-jail paths are still refused, that saving invalidates the status cache immediately, and that **a non-repository directory degrades to "no status" while reading files still works**.
  The whole layer is skipped when git is not installed on the machine (layer 1 still runs).
- **`verify-editors.mjs`**: three layers. (1) Parsing fixtures pin the text shapes the editor probe handles — the registry's `App Paths` `(Default)` value, `StartMenuInternet`'s `shell\open\command` (a quoted, argument-carrying form such as `"C:\…\chrome.exe" -- "%1"` must be stripped cleanly), the order of candidate names on `PATH` (Windows accepts only `.exe`, which comes first and appears once), and exact-then-prefix matching of registry key names (Firefox subkeys carry a client hash suffix, so `FIREFOX.EXE-308046b0af4a39cb` must match). (2) End to end: a stub host drives the **real `main.js`**, asserting the shape of `fm.editors`, the path and content of the on-disk cache, and the boundary that **the view never receives an executable path** (only an id and a display name); then a **second real process** reads the same cache, asserting identical results and that the cache file was not rewritten — that is what "probe once a day, share across windows" has to guarantee. (3) Path guards: an unknown editor id, a relative path escaping the root, a credential file, the `external` shape, and missing parameters are all refused. Finally one case **really launches**: the "editor" is set to `node` itself and the opened entry is a small script, with the assertion written by that real child process — the argument it received is the absolute path of the file that was clicked.
- **`verify-watch.mjs`**: three layers. (1) Pure decisions about noise and suppression: `.git/`, `node_modules/` at any level, credential paths, and this plugin's own atomic-write temp files (`.README.md.<ts>.<rand>.tmp`) are not reported, while a real file with the same name is; and the record/decide halves of the "did I write this myself" suppression. (2) End to end: a temporary directory plus a stub host drives the **real `main.js`**, asserting that **the operating system really delivered the events** — external modify / create / delete all appear in the cursor increment, asking twice with the same cursor is idempotent, changes under `.git/` and `node_modules/` stay out, **the plugin's own saves stay out**, a same-name change after the suppression window is reported again (the watch does not slowly fail), switching folders moves the watch along, with no project it reports unavailable instead of throwing, and `onUnload` really stops it. (3) The view's decisions (pure functions in `lib/watch.ts`): a change elsewhere only refreshes the directory, an open file changed with no unsaved edits is re-read, unsaved edits only raise a notice and are never overwritten, the number of refreshed directories is capped, and a cursor outside the history is handled conservatively.
- **`verify-pdf.mjs`**: a stub host drives the real `main.js` and verifies `.PDF` case-insensitive recognition, lossless base64 byte transfer, the 24 MiB boundary and over-limit handling, the path of empty / corrupt files into the PDF viewer, plus out-of-root paths, symlinks, credential restrictions, and multi-folder switching; it also checks the stable width of two-page covers / last pages, mixed-size grouping, lazy and out-of-order loading, and isolation between documents. PDF content routing and read-only behaviour are also covered by `verify-viewers.mjs`; rendering and interaction need a real browser.

PDF browser acceptance should use the production build and an offline `file://` page: continuous scrolling through a long document with the page bottom reachable, page-number sync, three layouts with mixed portrait and landscape pages fitting the width, scrolling back and forth across the single/double-page boundary at the cover and last page and zooming after dragging without changing scale or stopping render events, stable ratios after lazily loading a new size, thumbnail and nested/named bookmark jumps, the no-outline notice, page labels and Info / XMP metadata, real mouse text selection, rotated pages and unusual page units, Chinese font mapping and scanned / CMYK decoding, a 360 px narrow panel, theme and language, zoom after fast page changes, fast file switching, and recovery after a load or worker failure. After closing a PDF, confirm that both the worker and the Blob URLs are released; even once the browser-simulated host bridge passes, the real panel interaction still has to be checked in an installed PI-Desktop package.

## Data and security

**This plugin reads and writes files in the current project with its own Node `fs`, not through the host's `pi.fs` gateway.**

Why it has to be that way: the host's `manifest.fs` **forbids whole-tree writes syntactically** (a write scope cannot be `**`), and any narrower scope that passes validation turns every save into a permission prompt; on top of that, `pi.fs.*` has no create / rename / move, while `fs.glob` and `fs.list` are capped, skip `node_modules`, and mask credential paths. The corresponding cost is that **the host's permission gateway does not sit in front of these calls**, so the security responsibility belongs to the plugin. The manifest therefore declares no `fs.write` (write permission cannot honestly be declared at all) and declares only `ui.view` and `fs.read` — **the latter solely for the two actions the host alone can perform**, "open with the default application" and "reveal in folder" (`fs.openDefault` / `fs.reveal`, with the same permissions and scope as the built-in Files view: root `workspace`, scope `**`). The host validates those two channels against the declared scope and refuses anything out of bounds itself.

Every restriction the plugin enforces on its own:

| Restriction | Detail |
|---|---|
| Path containment | A relative path is accepted only relative to **the currently selected registered folder root**; absolute paths, `..`, and **symlinks / junctions** whose realpath lands outside that root are all refused. When a project registers several folders the containment base is still **one** root and never widens to the union of the group (changing the base only changes which door you came through; the rules behind it are identical); if a host-requested absolute path falls under another root of the same project, the base first switches to the root containing it and the path is then resolved relative to that root, with containment still fully enforced. The only exception is a host request to open a path outside the project (session scratch directory / attachments): allowed only when the view marks it `external: true`, with **no in-root containment check** (it is outside the root by definition), while the deny list and realpath checks still apply in full |
| Sensitive paths | `.env*`, `.ssh`, `.aws`, `.gnupg`, `.git/**`, `*.pem`, `*.key`, `*.p12` and similar are refused for both reading and writing; `node_modules` is readable but not writable |
| Atomic writes | Write a temporary file in the same directory → `fsync` → keep the original permission bits → `rename` over it, so an interruption never leaves a half-written file |
| Conflict detection | `mtimeMs` plus file size as an optimistic lock; a file changed outside the editor is **never silently overwritten** — a dialog first asks whether to overwrite, discard, or reload |
| Write audit | Every write appends a line to `write-audit.jsonl` in the plugin data directory (rotated at about 1 MiB), because the host cannot audit this path |
| Read-only database | Opened with `readOnly` plus `PRAGMA query_only = 1` (measured: `DROP`/`INSERT` are refused by SQLite itself), with a statement allowlist on top: only `select` / `with` / `values` / `explain` and read-only `pragma`, and only **a single** statement — `node:sqlite`'s prepare accepts multiple statements (measured: `select 1; select 2` runs only the first and raises nothing), so it has to be stopped here. Table and column names are checked against `sqlite_schema` before quoting; nothing is interpolated directly |
| Size limits | Text preview 2 MiB, images 8 MiB, audio/video and PDF 24 MiB each, writes 8 MiB. Image, audio/video, and PDF bytes travel to the view as base64 in the response (about a third larger), so they are limited separately; the notice names the exact limit |
| External editors | "Open with…" is `spawn`ed by the plugin's main process: the executable **can only come from the list the plugin probed itself** (the view passes an id, never a path), and the entry being opened first passes the same in-root containment check and credential deny list as every other channel; `spawn` does not go through a shell, the argument list is a single absolute path, and the child is `detached` + `stdio: ignore` + `unref`, so the editor outlives the panel and does not hold the plugin process; every launch records a write-audit line. On Windows only real `.exe` files count (`.cmd` / `.bat` shims would need `cmd.exe`, an unnecessary injection surface). Browsers appear only for web files (the pure function in `lib/editors.ts` filters by extension). Probing reads the registry and `PATH` and writes nothing, and results are cached per day in `editors.json` in the plugin data directory |

Two behavioural notes:

- The `.git` directory **never appears in the tree** (huge and never useful).
- Ignore rules come from `.gitignore` and `.ignore` (supporting `!` negation, a trailing `/`, a leading `/` anchor, and `*` / `?` / `**`). This is a subset of gitignore: `\` escapes and `[a-z]` character classes are not supported, and any deviation only affects whether something is shown — the toolbar's eye button reverses it at any time.

**How the Markdown preview stays safe**: the preview **does not use** `dangerouslySetInnerHTML`; it parses Markdown into React elements, so nodes are escaped by React and the injection surface does not exist structurally, which is why no extra sanitizer is needed. The reason is direct: this view's bridge leads to a plugin main process that can read and write project files, so an XSS in the preview equals arbitrary file writes. Links in the preview do not navigate either (one click would leave the plugin page with no way back); clicking only shows the address.

**No network access**: there is no `net.domains` and the runtime issues no requests. The plugin data directory holds only settings (split width, whether the left list is collapsed, display switches, the default Markdown view, which folder each project is viewing), the audit log above, and the day's editor probe cache (`editors.json`, holding only the paths of the programs found, one per day).

## Known limitations

- **Deleting asks first**: a directory is deleted recursively, with the same path restrictions as writes (inside the currently selected folder root, refusing the root itself and credential paths), and the deletion is recorded in the write audit; it cannot be undone.
- **"Open with the default application" and "reveal in folder" only work on files** (the host returns `INVALID_ARGUMENT` for directories); the entries are in the file tree's context menu.
- **Images in the Markdown preview are still placeholders**: `![](path)` renders as a placeholder carrying the file name. Viewing an image file through a data URI already works, but images inside the preview would each have to be read by relative path, which this round did not do. The reason is the same as above: the panel loads over `file://`, so a relative path points at the view itself rather than the project.
- **File watching**: the host has a single channel that pushes to views (`view:open`, used for "open this file" requests) and no file-change events, so external changes are not real-time; saving refreshes the directory, and the toolbar's **reload from disk** is always available to pull in changes made elsewhere (it asks first when there are unsaved changes).
- **Paths outside the project only when the host names them**: only a file the host asks to open may live outside the project root (session scratch directory / attachments), and the view must declare `external` explicitly; the tree itself still shows only the current project, and the plugin never browses outside it on its own.
- **One folder root at a time**: when a project registers several folders, the tree, search, SQLite, and every path check resolve against **the currently selected root** — switch at the top left to see another folder (switching rebuilds the view state). Folders in a group are never merged into one tree: there is exactly one containment base at any moment.
- **Binaries are not previewable**: zip / apk / exe / tiff only report a notice — no unpacking, no archive listing, no hex view. TIFF specifically: Chromium cannot decode it, so it is treated as binary rather than shown as a broken image.
- **Images, audio/video, and PDF are read-only**: viewing only, never in the editor and never modified (which does not affect editing other files).
- **Large files are not previewed**: images above 8 MiB and audio/video or PDF above 24 MiB only report the limit.
- **PDF passwords and scans**: a PDF that needs a password is reported with a suggestion to unlock it in the default application; this version offers no password input. Scans can be viewed but are not OCR'd and no selectable text is invented; a corrupt or unsupported PDF reports an explicit error.
- **`.avi` and similar are treated as binary** (Chromium cannot play them); whether `.mkv` / `.mov` plays depends on the codecs inside, and a clear notice appears when it cannot.
- **SQLite is read-only**: no writes, no VACUUM, no `-shm`. **Content not yet checkpointed from WAL mode is not visible** (the overview says so); encrypted databases (SQLCipher) and corrupt files both report "cannot read" instead of going silently blank.
- **Deep paging in a database is capped** (OFFSET ≤ 100,000 rows): `node:sqlite` is a synchronous API with no interruption hook, so queries have to be bounded by construction — narrow the range in the SQL box to go further.
- **Row counts in the table list are estimates** (`max(rowid)`): an exact `COUNT(*)` is a full scan on a large table, so run it in the SQL box when you need it.
- **The host runtime must provide `node:sqlite`** (Node ≥ 22.5; the current host, Electron 43 / Node 24, qualifies). When it is unavailable the plugin does not crash: it shows the overview and explains why.
